ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`company`.`employee`, CONSTRAINT `fk_employee_department` FOREIGN KEY (`Dno`) REFERENCES `department` (`Dnumber`))

Q1.3 DELETE
-----------
(a) Delete one dependent and one WORKS_ON row:

mysql> DELETE FROM dependent WHERE essn = '444444444' AND dependent_name = 'Ali';
Query OK, 1 row affected

mysql> DELETE FROM works_on WHERE essn = '222222222' AND Pno = 3;
Query OK, 1 row affected

(b) Try to delete a department that still has employees (4 Administration):

mysql> DELETE FROM department WHERE Dnumber = 4;
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`company`.`employee`, CONSTRAINT `fk_employee_department` FOREIGN KEY (`Dno`) REFERENCES `department` (`Dnumber`))

What happens: error 1451. The rows of EMPLOYEE (and PROJECT) still refer to
department 4, and the foreign keys use the default ON DELETE RESTRICT, so
MySQL refuses to delete the parent row while children point to it.

Order to remove the department: first remove (or move) every row that refers
to it, children before parents:
  1. WORKS_ON rows of its projects       (they refer to PROJECT)
  2. its PROJECT rows                    (they refer to DEPARTMENT)
  3. its EMPLOYEE rows: move them to another department (UPDATE ... SET Dno)
     - or delete them after deleting their WORKS_ON/DEPENDENT rows and
     clearing the super_ssn / mgr_ssn values that point to them
  4. finally the DEPARTMENT row itself.
Demonstration inside a transaction (rolled back, so our data is kept for the
next questions):

mysql> START TRANSACTION;
Query OK, 0 rows affected

mysql> DELETE FROM works_on WHERE Pno IN (10, 20);
Query OK, 2 rows affected

mysql> DELETE FROM project WHERE Dno = 4;
Query OK, 2 rows affected

mysql> UPDATE employee SET Dno = 1 WHERE Dno = 4;
Query OK, 2 rows affected

mysql> DELETE FROM department WHERE Dnumber = 4;
Query OK, 1 row affected

mysql> ROLLBACK;
Query OK, 0 rows affected

mysql> SELECT * FROM department WHERE Dnumber = 4;
+---------+----------------+-----------+----------------+
| Dnumber | Dname          | mgr_ssn   | mgr_start_date |
+---------+----------------+-----------+----------------+
| 4       | Administration | 666666666 | 2019-01-01     |
+---------+----------------+-----------+----------------+
1 row in set

(c) DELETE without WHERE inside a transaction:
Note for MySQL Workbench: Workbench turns on "safe updates", which refuses a
DELETE without a WHERE on a key (Error 1175). Run SET SQL_SAFE_UPDATES = 0;
first (the mysql command-line client does not need it).

mysql> SET SQL_SAFE_UPDATES = 0;
Query OK, 0 rows affected

mysql> START TRANSACTION;
Query OK, 0 rows affected

mysql> DELETE FROM dependent;
Query OK, 3 rows affected

mysql> SELECT * FROM dependent;
+------+----------------+--------+-------+--------------+
| essn | dependent_name | gender | bdate | relationship |
+------+----------------+--------+-------+--------------+
Empty set

mysql> ROLLBACK;
Query OK, 0 rows affected

mysql> SELECT * FROM dependent;
+-----------+----------------+--------+------------+--------------+
| essn      | dependent_name | gender | bdate      | relationship |
+-----------+----------------+--------+------------+--------------+
| 111111111 | Mariam         | F      | 1978-12-01 | Spouse       |
| 222222222 | Hany           | M      | 1980-10-14 | Spouse       |
| 333333333 | Laila          | F      | 2018-04-05 | Daughter     |
+-----------+----------------+--------+------------+--------------+
3 rows in set

What did the delete remove? A DELETE without WHERE removes EVERY row of the
table (here the 3 dependents left after Q1.3a); the SELECT inside the
transaction shows an empty table.
What did ROLLBACK do? It cancelled every change made since START TRANSACTION,
so the 3 dependents came back. (Without START TRANSACTION, autocommit would
have made the delete permanent.)

Q1.7 HAVING
-----------
(a) Departments with more than 2 employees:

mysql> SELECT Dno, COUNT(*) AS employees FROM employee GROUP BY Dno HAVING COUNT(*) > 2;
+-----+-----------+
| Dno | employees |
+-----+-----------+
| 5   | 5         |
+-----+-----------+
1 row in set

(b) Same, counting only the employees whose salary is above 3000:

mysql> SELECT Dno, COUNT(*) AS employees FROM employee WHERE salary > 3000 GROUP BY Dno HAVING COUNT(*) > 2;
+-----+-----------+
| Dno | employees |
+-----+-----------+
| 5   | 5         |
+-----+-----------+
1 row in set

(Same result as (a): after the 10% raise of Q1.2 all 5 Research employees
earn more than 3000, while Administration keeps only 1 such employee.)

WHERE vs HAVING: WHERE filters individual rows before they are grouped (so it
cannot use aggregate functions), while HAVING filters whole groups after
GROUP BY, using aggregate values such as COUNT(*).

Q1.10 LEFT JOIN
---------------
(a) Every department with its number of employees, including 0:

mysql> SELECT d.Dnumber, d.Dname, COUNT(e.ssn) AS employees FROM department d LEFT JOIN employee e ON e.Dno = d.Dnumber GROUP BY d.Dnumber, d.Dname ORDER BY d.Dnumber;
+---------+----------------+-----------+
| Dnumber | Dname          | employees |
+---------+----------------+-----------+
| 1       | Headquarters   | 1         |
| 4       | Administration | 2         |
| 5       | Research       | 5         |
| 6       | Marketing      | 0         |
+---------+----------------+-----------+
4 rows in set

(COUNT(e.ssn) and not COUNT(*): for Marketing the LEFT JOIN makes one row with
e.ssn = NULL, which COUNT(e.ssn) does not count.)

(b) Projects that nobody works on:

mysql> SELECT p.Pnumber, p.Pname FROM project p LEFT JOIN works_on w ON w.Pno = p.Pnumber WHERE w.Pno IS NULL;
